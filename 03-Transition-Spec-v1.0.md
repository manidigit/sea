# FlashLearn — Transition Specification

**Document:** `03-Transition-Spec-v1.0.md`  
**Status:** FROZEN  
**Predecessor:** `02-SEA-Final-Architecture-Spec-v1.2.md`  
**Purpose:** Deterministic review state-transition specification for implementation and testing.

---

## 1. Purpose

This document converts the frozen architecture's review rules into a deterministic state machine.

The specification defines:

- initial learning state
- review eligibility
- correct/incorrect transitions
- difficulty changes
- monthly wrong-count behavior
- timestamps
- ReviewHistory requirements
- ReviewSession lifecycle
- interruption/resume rules
- duplicate-answer protection
- deterministic ordering

Stage 04 and Stage 05 MUST derive their schema and queries from this specification.

---

## 2. State Model

Each Concept MUST have exactly one LearningState.

### Stages

```text
DAILY
WEEKLY
MONTHLY
LEARNED
```

### Difficulty

```text
EASY
MEDIUM
HARD
VERY_HARD
```

Difficulty is monotonic upward during normal failure escalation, except where the explicit MONTHLY-correct rule resets it to EASY after first-time successful completion of the learning path.

---

## 3. Initial State

When a new Concept becomes available for learning:

```text
stage = DAILY
difficulty = EASY
monthlyWrongCount = 0
totalCorrect = 0
totalWrong = 0
lastReviewedAt = null
nextReviewAt = immediate eligibility
```

`nextReviewAt` MUST be populated with a timestamp that makes the new item immediately eligible for its initial Daily review.

The exact timestamp MUST be generated by the application clock at creation time.

---

## 4. Review Eligibility

A scheduled card is eligible only when:

```text
nextReviewAt <= now
```

and:

```text
stage != LEARNED
```

unless the user explicitly starts an optional Learned review.

A review session MUST use a single captured `sessionNow` / evaluation clock for each submitted answer rather than deriving contradictory timestamps from multiple clock reads.

---

## 5. State Transition Function

Conceptually:

```text
transition(state, answer, now) -> newState
```

The function MUST be pure from the Domain perspective except for its supplied clock value and MUST NOT access Android, Room, DAO, ViewModel, or UI classes.

---

## 6. DAILY Transitions

### 6.1 Correct

Input:

```text
stage = DAILY
answer = CORRECT
```

Result:

```text
stage = WEEKLY
difficulty = unchanged
nextReviewAt = now + 7 days
monthlyWrongCount = unchanged
```

Counters:

```text
totalCorrect += 1
totalWrong = unchanged
lastReviewedAt = now
```

### 6.2 Incorrect

Input:

```text
stage = DAILY
answer = INCORRECT
```

Result:

```text
stage = DAILY
difficulty = unchanged
nextReviewAt = immediate eligibility
monthlyWrongCount = unchanged
```

Counters:

```text
totalWrong += 1
totalCorrect = unchanged
lastReviewedAt = now
```

The card does not advance to WEEKLY.

---

## 7. WEEKLY Transitions

### 7.1 Correct

```text
stage = MONTHLY
nextReviewAt = now + 30 days
difficulty = unchanged
monthlyWrongCount = unchanged
```

Counters:

```text
totalCorrect += 1
lastReviewedAt = now
```

### 7.2 Incorrect

```text
stage = DAILY
nextReviewAt = immediate eligibility
difficulty = max(currentDifficulty, MEDIUM)
monthlyWrongCount = unchanged
```

Counters:

```text
totalWrong += 1
lastReviewedAt = now
```

This transition MUST NOT reduce an already higher difficulty.

---

## 8. MONTHLY Transitions

### 8.1 Correct

```text
stage = LEARNED
nextReviewAt = null
```

If this is the first successful completion of the full path:

```text
difficulty = EASY
```

Otherwise:

```text
difficulty = unchanged
```

Counters:

```text
totalCorrect += 1
lastReviewedAt = now
monthlyWrongCount = unchanged
```

### 8.2 Incorrect

```text
monthlyWrongCount += 1
stage = DAILY
nextReviewAt = immediate eligibility
```

Difficulty:

```text
if monthlyWrongCount == 1:
    difficulty = HARD

if monthlyWrongCount > 1:
    difficulty = VERY_HARD
```

Counters:

```text
totalWrong += 1
lastReviewedAt = now
```

The monthly wrong count is cumulative for the Concept's learning lifecycle and is not reset by a subsequent correct Daily or Weekly answer.

---

## 9. LEARNED Review

A LEARNED Concept may be reviewed only through an explicit optional Learned-review flow.

Normal behavior:

```text
stage = LEARNED
stage remains LEARNED
nextReviewAt remains null
```

A ReviewHistory record MUST still be created.

Counters MUST reflect the answer:

```text
correct → totalCorrect += 1
incorrect → totalWrong += 1
lastReviewedAt = now
```

No normal Learned review may silently re-enter the scheduling state machine.

If a future feature introduces a Learned reactivation policy, it MUST be specified in a new version of this document.

---

## 10. Transition Table

| Current | Answer | Next | Difficulty | Next Review |
|---|---|---|---|---|
| DAILY | Correct | WEEKLY | unchanged | +7 days |
| DAILY | Incorrect | DAILY | unchanged | immediate |
| WEEKLY | Correct | MONTHLY | unchanged | +30 days |
| WEEKLY | Incorrect | DAILY | at least MEDIUM | immediate |
| MONTHLY | Correct | LEARNED | EASY only on first full-path success | none |
| MONTHLY | Incorrect | DAILY | HARD / VERY_HARD | immediate |
| LEARNED | Correct | LEARNED | unchanged | none |
| LEARNED | Incorrect | LEARNED | unchanged | none |

---

## 11. Immediate Eligibility

“Immediate” does not mean an arbitrary future delay.

For a failed card:

```text
nextReviewAt <= now
```

MUST be true after the transition.

A session-level exclusion rule MAY prevent the same card from appearing again immediately in the same active session, but this is a session presentation rule and MUST NOT alter the LearningState schedule.

---

## 12. ReviewHistory

Every accepted answer MUST create exactly one ReviewHistory record.

The record MUST capture the state before and after the transition.

Required values:

```text
conceptId
sessionId
reviewStage
reviewDate
isCorrect
previousStatus
newStatus
previousDifficulty
newDifficulty
responseTimeMs
```

`reviewDate` and `lastReviewedAt` MUST use the same logical evaluation timestamp for that answer.

ReviewHistory is append-only.

A later state transition MUST NOT modify historical records.

---

## 13. ReviewSession Lifecycle

### Start

When a user starts a review session:

```text
create ReviewSession
startedAt = now
endedAt = null
reviewType = selected type
```

### Answer

For every accepted answer:

```text
load current LearningState
validate eligibility
calculate transition
persist LearningState
append ReviewHistory
```

These operations MUST be treated as one logical transaction.

### Finish

When the session ends normally:

```text
endedAt = now
```

### Empty session

A session may contain zero answers.

It may still be closed normally with:

```text
startedAt != null
endedAt != null
```

---

## 14. Transaction Boundary

An accepted answer MUST NOT produce only part of its state change.

The following must succeed or fail together:

```text
LearningState update
ReviewHistory insert
review counter update
```

If persistence fails, the application MUST NOT report the answer as successfully committed.

The UI may retry the operation using the duplicate-protection rules below.

---

## 15. Duplicate-Answer Protection

The same user action MUST NOT be committed twice.

Each submitted answer MUST have an idempotency identity at the application/session level.

Recommended:

```text
sessionId + conceptId + reviewAttemptId
```

`reviewAttemptId` is generated once when the answer action is accepted.

A retry of the same operation MUST return the already committed result instead of creating a second ReviewHistory record or applying the transition twice.

Two genuinely separate attempts may create two records only when the first attempt has completed and the application has explicitly presented the card again according to session rules.

---

## 16. Session Interruption

If the application is backgrounded, closed, or otherwise interrupted:

- already committed answers remain committed
- ReviewHistory remains intact
- the ReviewSession may remain open until recovery/finalization
- uncommitted UI state MUST NOT be treated as an answer

On resume:

```text
reload persisted session state
reload current LearningState
continue with the next eligible card
```

The application MUST NOT reconstruct an answer from an unpersisted UI state.

---

## 17. Card Ordering

Ordering MUST be deterministic.

Within a selected review type:

1. eligible cards are filtered by stage and `nextReviewAt`
2. cards already answered in the current session are excluded unless explicitly configured otherwise
3. the remaining set is ordered by:
   - earliest `nextReviewAt`
   - then stable `Concept.id`

This guarantees repeatable ordering when timestamps are equal.

Randomized presentation, if later introduced, MUST use a separate presentation-layer policy and MUST NOT change state-transition semantics.

---

## 18. Review-Type Eligibility

### DAILY session

Select Concepts whose stage is:

```text
DAILY
```

and whose schedule is immediately eligible.

### WEEKLY session

Select Concepts whose stage is:

```text
WEEKLY
```

and:

```text
nextReviewAt <= now
```

### MONTHLY session

Select Concepts whose stage is:

```text
MONTHLY
```

and:

```text
nextReviewAt <= now
```

### LEARNED session

Only explicit optional review may select:

```text
LEARNED
```

Learned cards are not automatically scheduled.

---

## 19. Counters

### totalCorrect

Increment once for every accepted correct answer.

### totalWrong

Increment once for every accepted incorrect answer.

### monthlyWrongCount

Increment only when a MONTHLY-stage answer is incorrect.

It MUST NOT increment for:

```text
DAILY incorrect
WEEKLY incorrect
LEARNED incorrect
```

It MUST NOT be reset by normal successful transitions.

---

## 20. Difficulty Rules

Difficulty ordering:

```text
EASY < MEDIUM < HARD < VERY_HARD
```

The WEEKLY incorrect transition applies:

```text
difficulty = max(currentDifficulty, MEDIUM)
```

The first MONTHLY incorrect transition produces:

```text
HARD
```

A subsequent MONTHLY incorrect produces:

```text
VERY_HARD
```

The MONTHLY correct transition may set difficulty to EASY only when the Concept has completed the full path successfully for the first time.

---

## 21. First-Time Full-Path Success

For the purpose of the MONTHLY-correct rule, “first-time success through all stages” means:

```text
Concept was created
→ DAILY correct
→ WEEKLY correct
→ MONTHLY correct
```

with no prior incorrect transition that requires restarting the learning path.

If the Concept has previously failed at WEEKLY or MONTHLY, a later successful MONTHLY answer MUST NOT qualify as first-time full-path success.

Therefore:

```text
firstTimeSuccessAllStages = true
```

only for a clean first pass through:

```text
DAILY → WEEKLY → MONTHLY → LEARNED
```

---

## 22. Failure and Restart Semantics

“Restart” means restarting the learning stage at:

```text
DAILY
```

It does NOT mean resetting:

```text
monthlyWrongCount
totalCorrect
totalWrong
ReviewHistory
Concept identity
Content
```

Difficulty also does not automatically reset when a Concept returns to DAILY.

---

## 23. Clock Semantics

All scheduling uses a single authoritative application clock.

The Domain transition function receives:

```text
now: Instant
```

The Domain MUST NOT call system time directly during transition calculation.

This makes transitions deterministic and unit-testable.

Intervals are calendar-independent durations for the state machine:

```text
7 days
30 days
```

The resulting `nextReviewAt` is calculated from the accepted answer timestamp.

---

## 24. Required Domain Test Matrix

At minimum, automated tests MUST cover:

### DAILY

```text
correct → WEEKLY
incorrect → DAILY
correct → +7d
```

### WEEKLY

```text
correct → MONTHLY
incorrect → DAILY
incorrect from EASY → MEDIUM
incorrect from HARD → HARD
incorrect from VERY_HARD → VERY_HARD
correct → +30d
```

### MONTHLY

```text
first clean correct → LEARNED + EASY
first incorrect → DAILY + HARD + count 1
second incorrect → DAILY + VERY_HARD + count 2
later incorrect → DAILY + VERY_HARD
```

### LEARNED

```text
correct → LEARNED
incorrect → LEARNED
history created for both
```

### Integrity

```text
one accepted answer → one history record
retry same attempt → no duplicate transition
failed transaction → no false success
session interruption → committed answers preserved
```

## 25. Implementation Constraints

The following classes belong conceptually to the Domain layer:

```text
ReviewStage
Difficulty
ReviewAnswer
LearningState
ReviewTransition
ReviewTransitionEngine
```

Suggested API:

```kotlin
fun transition(
    state: LearningState,
    answer: ReviewAnswer,
    now: Instant
): ReviewTransition
```

The returned transition should contain enough information for the application layer to persist both:

```text
new LearningState
ReviewHistory
```

without reproducing business rules in the ViewModel.

## 28. Frozen Invariants

1. Every Concept has exactly one LearningState.
2. Every accepted answer creates exactly one ReviewHistory record.
3. ReviewHistory is append-only.
4. State transition and history insertion are one logical transaction.
5. DAILY correct advances to WEEKLY.
6. WEEKLY correct advances to MONTHLY.
7. MONTHLY correct advances to LEARNED.
8. DAILY incorrect remains DAILY.
9. WEEKLY incorrect returns to DAILY and raises difficulty to at least MEDIUM.
10. MONTHLY incorrect returns to DAILY and increments monthlyWrongCount.
11. First MONTHLY failure produces HARD.
12. Subsequent MONTHLY failures produce VERY_HARD.
13. Monthly wrong count is cumulative.
14. Failed transitions do not reset lifetime counters.
15. Learned review does not automatically reactivate a Concept.
16. Scheduling is based on `nextReviewAt <= now`.
17. Transition calculation is deterministic from state, answer, and supplied time.
18. ViewModels do not implement transition rules.
19. Stage 04 and Stage 05 must not redefine the learning algorithm.
